# Android stream decisions

Decisions taken without the user present while building the phone app
(`android/`, package `de.kruse.stopmotion`). One row per thing that was
ambiguous, blocking, or where the plan left a choice open.

| area | roadblock | decision | rationale |
|---|---|---|---|
| toolchain | Plan.md fixes Gradle 8.14 but not AGP/Kotlin | AGP 8.13.0, Kotlin 2.2.20, JDK 17 target, compileSdk/targetSdk 36, minSdk 26 | AGP 8.13 is the newest stable that requires Gradle >= 8.13 and JDK 17, and it knows compileSdk 36; Kotlin 2.2.20 is stable against Gradle 8.14. Verified by a clean `assembleDebug`. |
| dependencies | CameraX latest release on the repo is 1.7.0-alpha03 | Pinned CameraX 1.4.2 (core, camera2, lifecycle, view) | Newest stable line. `Camera2Interop`, `Camera2CameraControl` and `ResolutionSelector` are all settled APIs there; an alpha would add churn to a build nobody can smoke-test on hardware. |
| HELLO payload | `CameraCapabilities.from_hello` on the desktop is written by another stream; unknown whether it tolerates unknown keys | HELLO carries **exactly** the eight keys in docs/interfaces.md and nothing else | If `from_hello` ever does `cls(**hello)` an extra key is a hard failure, while the missing extras cost nothing. Device-only values (max still size, MANUAL_SENSOR support) are kept phone-side. |
| PREVIEW_CTL | Plan.md only says JSON `{start\|stop}`; the exact key shape is unspecified | Phone accepts `{"start":true}`, `{"stop":true}`, `{"on":bool}`, `{"enabled":bool}` and `{"action":"start"}` | Cheap to accept all plausible shapes rather than guess wrong and have the preview silently never start. Whatever the desktop stream picked will work. |
| PING/PONG | Plan.md calls the payload "empty", but the framing always has a 2-byte header length | Sends `{}` as the header (payload = 4 bytes); the reader also tolerates a bare type byte with no header at all | Keeps every message uniform for the codec while staying compatible if the desktop emits a truly empty payload. |
| SET_CONFIG | Unspecified whether the desktop always sends the full settings block | Treated as a partial merge over the phone's current state; absent keys keep their value | A partial update can never be misread as "reset everything to defaults", and a full block behaves identically. |
| manual controls | Changing exposure/ISO/focus via `Camera2Interop.Extender` alone would need a rebind per change | Extender sets the initial values at bind time; every later change goes through `Camera2CameraControl.setCaptureRequestOptions` | Rebinding drops frames and re-runs 3A. Only a change of analysis resolution rebinds, because that is baked into the use case. |
| AF lock | Camera2 has `CONTROL_AE_LOCK` and `CONTROL_AWB_LOCK` but no `CONTROL_AF_LOCK` | `af_lock` is expressed as `CONTROL_AF_MODE = OFF` with the requested `LENS_FOCUS_DISTANCE` | A fixed manual focus distance *is* the lock. On MANUAL_SENSOR devices AF is off permanently anyway; on others the flag switches between OFF and CONTINUOUS_PICTURE. |
| no MANUAL_SENSOR | Some devices do not advertise `REQUEST_AVAILABLE_CAPABILITIES_MANUAL_SENSOR`, so AE_MODE=OFF is ignored | Fall back to `CONTROL_AE_MODE=ON` plus AE/AWB lock, and surface "(no manual sensor)" in the on-screen status | Flicker-free stopmotion needs locks more than it needs absolute numbers (Plan.md section 7). Failing loudly on screen beats pretending the values were applied. |
| focus range | `LENS_INFO_MINIMUM_FOCUS_DISTANCE` is a diopter maximum, not a minimum | HELLO reports `focus_diopters {lo: 0.0, hi: minimumFocusDistance}` | 0 diopters is infinity and the reported value is the closest focus. The desktop slider then runs infinity -> macro left to right. |
| preview rotation | `PREVIEW_FRAME` header is only `{seq, w, h}`, so there is nowhere to put an orientation | The NV21 buffer is rotated by `ImageInfo.rotationDegrees` before JPEG encoding; `w`/`h` report the post-rotation size | The desktop gets an upright frame with no EXIF to interpret. In locked landscape the rotation is normally 0, so the cost is usually nil. |
| preview encoding | `YuvImage.compressToJpeg` needs NV21, CameraX analysis gives YUV_420_888 | Hand-written plane packer honouring row/pixel strides, on a dedicated `stopmotion-analysis` thread, with `STRATEGY_KEEP_ONLY_LATEST` | No Bitmap allocation per frame and no main-thread work. Matches the "drop frames rather than queue" requirement. |
| socket writes | A full-res still (several MB) must not interleave with preview frames | Every message is serialised into one byte array and handed to a single `stopmotion-writer` thread through a bounded queue | One writer means one message on the wire at a time, by construction rather than by locking discipline. |
| backpressure | What to do when the writer is busy during a capture | Preview frames are dropped past 2 queued; CONFIG_ACK / CAPTURE_RESULT / ERROR / HELLO block up to 5 s rather than drop | Plan.md already accepts that preview pauses during a capture. Control replies are not droppable - the desktop is waiting on them. |
| server lifecycle | Unspecified when exactly the socket should be up | `ServerSocket` starts in `onStart` and stops in `onStop`; the camera is released in `onDestroy`; a client disconnect stops the encoder and returns to listening | Ties the socket to the visible, screen-on activity. `FLAG_KEEP_SCREEN_ON` means a shoot never hits `onStop` accidentally. |
| camera selection | Requirements do not mention a front camera | `CameraSelector.DEFAULT_BACK_CAMERA` only, with a clear error if absent | The rig points a back camera at a set; a selector would be UI nobody wants on the phone. |
| capture storage | Hard user requirement: nothing written to phone storage | `takePicture(executor, OnImageCapturedCallback)`; no storage permissions in the manifest; JPEG bytes are copied out of the `ImageProxy` and handed straight to the socket | The file-based `takePicture` overload is never referenced, and without storage permissions there is no path to disk even by accident. |
| UI | Requirement: no shutter button | The layout has a `PreviewView` and a status overlay and nothing tappable | Restated here because the absence is deliberate: a button on the phone would nudge the rig at exactly the wrong moment. |
